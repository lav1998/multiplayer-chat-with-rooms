# AI Pairing Prompts Chronology

The following prompts document the incremental, step-by-step development process used with the AI assistant to build this application.

1. `I need to build a small interview assignment: a multiplayer chat application where users can join rooms and exchange messages in real time. I want to build this incrementally rather than having you generate the entire application at once. Let's start with the simplest possible working Python web application. Use FastAPI and Uvicorn and serve a very basic HTML page from the application. For now, I only want to prove that the Python backend starts successfully and the browser can reach it. Please create the minimal project structure and code needed for that. Don't implement chat, WebSockets, rooms, authentication, databases, or styling yet. After making the changes, tell me what you created and how I can run it locally. Don't commit anything to Git.`
2. `The basic application is running successfully. Before I make the first commit, add a .gitignore so generated files such as __pycache__, other files, and the local virtual environment are not committed. Don't change any application code + don't commit anything.`
3. `Great. Next now. LEt's move to frontend. What is the simplest browser UI we need before connecting it to the backend?`
4. `Yes. Go ahead and update index.html . Keep it minimal and semantic. Add only the HTML structure and the IDs/classes we'll need later for JavaScript. Don't implement WebSocket communication yet and don't add unnecessary styling or dependencies. After updating it, briefly explain the structure you chose.`
5. `The UI looks fine andready for now. Now let's think about how the browser should communicate with the Python backend for real time messaging. What is the simplest approach for this application, and why?`
6. `Yes. Let's implement the simplest possible WebSocket connection first. Add a WebSocket endpoint to the FastAPI backend and connect to it from the browser. For now, don't implement rooms or broadcasting. I just want to prove the basic connection lifecycle works as follows... [listed 8 steps]. Keep the implementation simple and use native browser WebSockets. Don't add new dependencies unless ACTUALLY necessary...`
7. `The echo works. Now we need multiple users and rooms. Before implementing it, what state does the server need to maintain to know which connected clients belong to which room?`
8. `Yes, let's implement the Connection Manager. Keep it deliberately small and focused on the requirements of this assignment. Use an in-memory mapping of room names to sets (and not lists) of active WebSocket connections. The manager should be responsible for: adding a connection, removing a connection, broadcasting a message...`
9. `Ok excellent, I tried running the chat room with multiple users and rooms in separate browsers. It is working as intended but before adding more features, I want to review the reliability of the current WebSocket implementation. Consider what happens if one WebSocket connection disappears unexpectedly while the server is broadcasting a message to a room. Also tell me - What could go wrong...`
10. `OK Implement the broadcast logic. A failed send message to one websocket must not prevent others from receiving the message. Also track whose send is failed. Remove failed connections after the broadcast loop rather than modifying the set while iterating over the set. Keep the existing normal disconnect handling...`
11. `Epic. The core realtime chat is now working fine. I'd like to add message timestamps next. Before changing the code, let's think about the message format. Currently the server sends plain text... What would be a simple message structure that lets the server send username, message text & timestamp while keeping the implementation lightweight?`
12. `sure, let's implement the JSON message format. Keep the change focused on message structure and timestamps. Chat messages should be sent as JSON. Add type identifier too! Include in message: -type -username -text -timestamp...`
13. `I tried passing whitespace only in text, it is not accepting it. inspect the current code and explain what happens, and whether you think we should validate it on the server, browser or both.`
14. `Yes. Implement the validation on both sides. Frontend: - Trim leading and trailing whitespace before sending. - Do not send the message if the resulting text is empty. Backend: - Strip leading and trailing whitespace from received messages...`
15. `Lovely. the chat functionality is working and tested. Let's do one small UI polish pass before we move on to testing and documentation. Add minimal CSS to make the chat application clean and easy to demo: - centered chat - clear room/username controls...`
